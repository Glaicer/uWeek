## Agent skills

### Issue tracker

Issues and specs live as local Markdown under `.scratch/<feature>/`. See `docs/agents/issue-tracker.md`. `.scratch/` is local-only and stays out of git: never `git add -f` it, even to commit a ticket's status change.

### Triage labels

Use the five default triage roles as status strings. See `docs/agents/triage-labels.md`.

### Domain docs

Single-context: root `GLOSSARY.md` and `docs/adr/`. Before exploring domain concepts or decisions, read `docs/agents/domain.md`.

`/docs/` is in `.gitignore`, but its files are tracked: add a new file there with `git add -f`, or it never reaches git.

### Default tech stack

Before choosing a library or tool for a task, read `docs/tech-stack.md`: accepted defaults (zustand 5.0.15, zod 4.6.7), the approved `uweek-cloud` stack (drizzle + pg, better-auth, resend, MCP server v2, zod-openapi, rate-limiter-flexible, vitest) with the ticket that installs each package, the explicit "not adopted" list with reasons, and the rules for adding any new dependency (resolve the current stable from the registry, pin the exact version, respect the spec's "no dependency unless used now" constraint). New dependencies are installed only with the owner's approval.

### Icons

Icons are Boxicons from https://icon-sets.iconify.design/boxicons: copy the SVG inline as a small component with `aria-hidden="true"`, `fill="currentColor"` and `1em` size (see `EditIcon` and `CalendarIcon` in `app/week.tsx`); no icon package.

### CSS anchors

CSS Modules rename dashed idents, so an `anchor-name` set inline (`style={{ anchorName }}`) never matches a `position-anchor` written in a `.module.css`: set both on the same side (see `Dropdown` in `app/week.tsx`).

### Tests

`pnpm dev`, `pnpm test` and `pnpm test:e2e` start Postgres themselves (`pnpm db:up`); every `next dev` (the owner's `pnpm dev` on `uweek`, Playwright's on `uweek_test`) applies migrations on start and again whenever `drizzle/meta` changes (`instrumentation.ts`), so a newly generated migration reaches a running dev server. That makes a generated migration live the moment it is written: never delete and regenerate one to fix it, generate a follow-up instead (a regenerated file gets a later `when`, and the dev database that already ran the first draft tries to apply it again); vitest migrates `uweek_test` in its global setup. Playwright starts its own `next dev` with `NEXT_DIST_DIR=.next-e2e` so it can run beside the owner's `pnpm dev` (Next allows one dev server per dist dir); keep the `.next-e2e` entries in `tsconfig.json`, or every test run rewrites the file. Sign-in emails land in `test-results/outbox` via `MAIL_OUTBOX_DIR`.

`pnpm test` (vitest) runs integration tests from `src/**/*.test.ts` against `uweek_test`. Keep them out of `tests/`: that is Playwright's `testDir`, and it would pick up any `*.test.ts` there.

### Branches

Never commit to `main`, even when asked to commit while on it (this overrides the global rule): switch to `dev` first. Small changes go to `dev`; a large feature gets its own branch from `dev` and merges back into `dev`. Releases are a pull request `dev` → `main` merged with a merge commit; an urgent fix is a `hotfix/*` branch from `main` with a pull request to `main`, then `main` merged into `dev`. See `docs/development.md`.

### Deploy

`README.md` is for users and lists features only; developer setup, checks and branches go in `docs/development.md`, deployment in `docs/self-hosting.md`. The repo is meant to be public: the VPS side (Postgres compose, certificates, backups, fail2ban) lives in the owner's private infrastructure repo, never here. Production is the Vercel project `u-week` (team `glaicers-projects`), built from `main`; its build runs `pnpm db:migrate` against the production database before `next build`, so a migration merged to `main` reaches real data on the next push.
